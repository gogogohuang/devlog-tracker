# Files Verify (machine-verified `#### 檔案`)

Devlog SSOT Phase 4. Extends the write-time verification `#### 工作區`
already gets (`docs/design/devlog-as-ssot-assessment.md`, Phase 1 —
`hooks/scripts/workspace-snapshot.sh`) to the other Handoff field that
makes a factual claim about the tree: `#### 檔案`. Today `#### 工作區`
is machine-verified against live git; `#### 檔案` is free prose nobody
checks — a round can say "新增 a.ts、b.ts" while `a.ts` was never
touched, or omit a file that really was changed, and nothing catches
it. This closes that gap the same way Phase 1 closed it for `工作區`:
Stop computes the actual answer itself and blocks the turn unless
`#### 檔案` matches.

This does **not** make `devlog.md` SSOT for file state — same scoping
as Phase 1 (`docs/design/devlog-as-ssot-assessment.md`'s "gap #1"
discussion). It makes the `#### 檔案` cache honest at `T_close`. git
remains the live source of truth.

## Decisions (grilling session, 2026-09-11)

These were settled interactively before writing this doc — recorded
here so the "why" survives, not just the "what":

1. **Scope: path-level, not semantic.** Verify that the paths listed
   under `#### 檔案` actually changed in git (added/modified/deleted),
   not whether `### Summary` / `決策` / `現況` prose is truthful. That
   broader "does the narrative match reality" problem is out of scope
   — it needs judgment, not a git diff.
2. **Mechanism: deterministic script, Stop-hook enforced** — same
   pattern as `workspace-snapshot.sh`, not a Claude self-review step.
   This plugin's core value is machine verification, not asking Claude
   to grade its own homework.
3. **No separate on/off switch.** Unlike Segment Watch / Checkpoint
   Mode, this has no dedicated command. It's part of what "強制記錄"
   already means, exactly like `#### 工作區` has none.
4. **Committed vs uncommitted paths need different verification
   strength**, because of a fact already on record in
   `skills/devlog-tracker/SKILL.md`: *"髒檔是整棵樹的未提交，不必跟
   『檔案』那輪 delta 相同"* — the working tree's dirty set can include
   leftovers from earlier, still-uncommitted rounds. So:
   - **Committed paths** (a `commit <hash>` block): exact,
     bidirectional, category-precise match against
     `git diff-tree --name-status`. A commit's content is unambiguous
     and unaffected by cross-round residue, so there's no reason to be
     lenient.
   - **Uncommitted paths** (`尚未 commit` block): one-directional
     subset check only — every path Claude claims must really be dirty
     right now, but the actual dirty set may contain more (unclaimed
     residue from a prior round is not an error). Category (新增 vs
     修改 vs 刪除) is **not** checked here, only path membership —
     catches "claimed a path that never changed" (the main failure
     mode) without demanding Claude re-litigate ambiguous
     staged/unstaged git states.
5. **Renames are not a fourth category.** git's rename detection is
   itself a similarity heuristic, not ground truth. `#### 檔案` keeps
   its existing three categories (新增/修改/刪除); a rename is
   represented as 刪除 `<old>` + 新增 `<new>`. Achieved for free by not
   passing `-M`/`--find-renames`/rename-detecting flags anywhere in
   `files-snapshot.sh` — plain `git status --short --no-renames` and
   `git diff-tree` (no `-M`) already report a rename as a straight
   delete+add pair.
6. **Mixed rounds are real and must be representable.** A round often
   commits partway through, then keeps editing. `#### 檔案`'s machine
   format supports any number of `commit <hash>：` blocks (chronological
   order) plus at most one trailing `尚未 commit：` block, not a
   whole-round "which one applies" choice.
7. **`.devlog/` is excluded from every comparison.** `devlog.md` and
   friends change every round as bookkeeping, not as "what this round's
   work touched." `files-snapshot.sh` filters any path under `.devlog/`
   out of both the computed-actual and the parsed-claimed sides, in
   both the committed and uncommitted branches — same rationale as
   `#### 工作區` already implicitly having nothing to say about
   `.devlog/` itself.

## Format: `#### 檔案`'s new machine-checked shape

Existing prose convention ("新增/修改/刪除的路徑；有 commit 就寫 hash
或說明沒 commit") becomes a fixed block grammar, generated by
`files-snapshot.sh` and copied in verbatim — same authoring model as
`#### 工作區`.

```
commit a1b2c3d：
新增：a.ts, b.ts
修改：c.ts

commit f9e8d7c：
修改：d.ts

尚未 commit：
修改：e.ts
刪除：f.ts
```

Grammar:

- Zero or more `commit <short-hash>：` blocks, in the order the commits
  were made, each followed by up to three category lines (新增/修改/刪除
  — same labels as today, omit categories with nothing to report).
- At most one trailing `尚未 commit：` block, same three category
  labels, for whatever is still dirty and belongs to this round.
- A round that touched no files outside `.devlog/` omits `#### 檔案`
  entirely — unchanged from today's "沒動檔就整節省略" rule.
- Blocks are separated by a blank line for readability; the parser
  only anchors on the header lines, so the blank line is not load
  bearing.

## `files-snapshot.sh`

New helper, sibling to `workspace-snapshot.sh`, sourced by
`enforce-devlog.sh`.

```
files_snapshot(dir)              # uncommitted branch
files_snapshot(dir, commit_hash) # committed branch
```

**Uncommitted branch** (`files_snapshot "$dir"`):

1. `git -C "$dir" status --short --no-renames` (no-renames per
   Decision 5).
2. Drop any line whose path is under `.devlog/`.
3. Categorize by the status letters (`??`/`A` → 新增, `M` in either
   column → 修改, `D` in either column → 刪除).
4. Emit up to three lines, same shape as the manual convention today:
   `新增：a, b`, `修改：c`, `刪除：d` — omit empty categories. Empty
   result (nothing outside `.devlog/` is dirty) prints nothing.

**Committed branch** (`files_snapshot "$dir" "$hash"`):

1. First verify the hash resolves: `git -C "$dir" rev-parse --verify
   -q "${hash}^{commit}"`. Unresolvable → caller treats as fail-open
   (see below), not as "empty diff."
2. `git -C "$dir" diff-tree --no-commit-id --name-status -r "$hash"`
   (no `-M`, per Decision 5).
3. Drop `.devlog/` paths, categorize `A`→新增, `M`→修改, `D`→刪除
   (diff-tree's letters are already unambiguous — no staged/unstaged
   mixing like working-tree status has).
4. Same three-line output shape.

Both branches share the categorize-and-format tail; only the git
command and the hash-existence pre-check differ.

## Wiring into `enforce-devlog.sh`

Runs inside the existing Stop-hook flow, alongside (not instead of)
the `#### 工作區` check, whenever the last Round's `#### 檔案` is
non-empty — which already covers `IN_PROGRESS` / `BLOCKED` (工作區 is
mandatory there anyway) and `DONE` with non-empty `檔案` (the
2026-09-11 workspace extension's existing trigger condition). Trivial
`DONE` rounds with no `#### 檔案` are untouched, same as today.
`INTERRUPTED` stubs never carry `#### 檔案` by convention and stay
unaffected.

1. Read `#### 檔案`'s body (`handoff_subsection_body '^#### 檔案'`,
   the same extractor Phase 1/2 already added).
2. Parse it into blocks by header line. A line that isn't a
   recognized header (`^commit [0-9a-f]{4,40}：$` or `^尚未
   commit：$`) and isn't a category line inside an open block is a
   **format violation** → block (exit 2), print the expected block
   grammar — same rigor `#### 工作區` already has for its seven
   formats. This is a Claude-authoring-format problem, not a
   fail-open case.
3. For each `commit <hash>` block:
   - `git` unavailable, or the hash fails to resolve → fail-open
     (skip just this block's check; don't block the turn on
     infrastructure trouble).
   - Otherwise compute `files_snapshot "$PROJECT_DIR" "$hash"` and
     compare **exactly** (full text, all categories) against the
     block's body. Mismatch → block, print the expected text for that
     hash, matching the "print the exact expected text so Claude can
     paste it verbatim" pattern Phase 1 established.
4. For the `尚未 commit` block (if present):
   - `git` unavailable → fail-open.
   - Compute `files_snapshot "$PROJECT_DIR"` for the actual dirty set.
   - Union all paths Claude listed across that block's category lines
     (category label itself is not checked, per Decision 4).
   - Every claimed path must appear somewhere in the actual dirty set
     (any category). Any claimed path that isn't actually dirty →
     block, print the actual current `files_snapshot` output so Claude
     can see what's really there and correct the claim. Extra actual
     dirty paths Claude didn't claim are **not** an error (cross-round
     residue, Decision 4) — this check is one-directional only.

Fail-open scope mirrors Phase 1 precisely: git missing, a git command
erroring unexpectedly, or a commit hash that doesn't resolve all skip
that block's check silently. A `#### 檔案` that doesn't parse into the
block grammar at all is not fail-open — Claude is expected to produce
the grammar `files-snapshot.sh` outputs, same as `#### 工作區`.

## Known limitations

- **Path containing a space.** Same limitation `workspace-snapshot.sh`
  already has for `未提交：` lists — the comma-joined single-line
  format isn't unambiguously reversible for such a path.
- **Copies (`git status`'s `C` code).** Not specifically handled;
  falls through the categorizer same as an unrecognized status letter
  would — treated conservatively (see implementation) rather than
  silently miscategorized.
- **A `尚未 commit` claim about a path that's actually staged AND has
  further unstaged changes** (git's `MM` etc.) still just counts as
  "dirty" — category-agnostic membership only, so this doesn't
  surface as an error, by design (Decision 4).
- **Does not verify prose.** `決策` / `現況` / `Summary` narrative
  truthfulness is explicitly out of scope (Decision 1) — this only
  catches path-level fabrication or omission in `#### 檔案`.
